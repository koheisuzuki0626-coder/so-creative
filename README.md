## 公開範囲

いまは **URL を知っている人だけに見せる** 設定にしている。

- `index.html` / `about.html` の `<meta name="robots" content="noindex, nofollow">`
- `robots.txt` から `Sitemap:` の行を外している

検索結果には出ないが、**アクセス制限ではない**。URL を知っていれば誰でも見られるし、
リポジトリが public なのでソースも読める。パスワードをかけたい場合は
GitHub Pages では対応できないため、別のホスティングが必要。

`robots.txt` で `Disallow: /` にしていないのは意図的。クロールを止めると
`noindex` 自体を読んでもらえず、外部リンク経由で URL だけ検索結果に出ることがある。

### 検索に載せたくなったら

1. 両ページの `<meta name="robots">` の行（とその上のコメント）を削除
2. `robots.txt` に `Sitemap: <公開URL>sitemap.xml` を戻す
3. Google Search Console でサイトを登録し、`sitemap.xml` を送信

`sitemap.xml` はそのまま置いてあるので作り直しは不要。

## 公開URLを変えるとき

canonical / og:url / og:image / 構造化データ / sitemap.xml / robots.txt には
絶対URLが必要で、いま17か所に散っている。1か所でも直し忘れると検索エンジンに
古いURLを伝え続けることになるため、まとめて書き換えるスクリプトを用意している。

```bash
node scripts/set-site-url.mjs --show                    # いまの設定を表示
node scripts/set-site-url.mjs https://example.jp/       # 独自ドメインへ(CNAME も生成)
node scripts/set-site-url.mjs https://xxx.github.io/    # github.io へ(CNAME は削除)
```

独自ドメインを指定した場合は、このあと GitHub 側で
**Settings → Pages → Custom domain** の設定と **Enforce HTTPS** が必要。

## 配色（2026-09-25 に濃色へ）

地の色は 白 → ごく薄い緑 → **濃色（チャコール／緑みのグレー）** と動かした。
墨・深緑寄りの黒・濃い緑そのもの・チャコールの4案を実ページに当てて見比べて選んでいる。
**形は変えていない。色だけを反転させた。**

| | 値 | 何 |
|---|---|---|
| `--bg` | `#1d201f` | 地 |
| `--bg-alt` | `#262b29` | 交互の帯 |
| `--card` | `#2c3230` | カード・パネル。地より一段明るくして浮かせる |
| `--bg-deep` | `#0d0f0e` | 全幅の黒い帯（ステージ・CTA）。地より暗い |
| `--ink` | `#f2f4f3` | 見出し・本文 |
| `--ink-2` | `#d4d8d6` | 読ませる本文 |
| `--ink-dim` | `#9ba29e` | 補助。地 6.30 ／ 帯 5.52 ／ カード 5.02（AA は 4.5） |
| `--on-ink` | `#1d201f` | `--ink` を**背景に敷いた**ときの文字色 |
| `--line` / `--line-strong` | 白の 12% / 28% | 罫線 |

### やったときにつまずいた所

- **`color: #fff` を一律に残さない。** `background: var(--ink)` のボタン（ナビの「相談する」、
  計算機の丸数字）は、`--ink` がほぼ白になった時点で白地に白になる。`--on-ink` を作って当てている
- **`color-scheme: dark` を書く。** 無いと `select`・スクロールバー・動画の操作部だけが
  ブラウザ既定の白で描かれ、計算機の尺・ナレーションの選択肢が浮く
- **ヒーローの映像は薄くする（0.22 → 0.16）。** 重ね方が同じでも、まわりが暗いと
  映像だけが浮いて主役に見える
- **暗い側は階調の段差が帯として見える。** OGP のにじみがそう。
  `scripts/recolor-ogp.py` は傾斜のある範囲にだけ粒を置いて散らしている
- **グラフの色は測り直す。** ロードマップの紫は濃地でコントラスト 2.87 と 3:1 を割ったので
  `#7c4dbf` → `#9370da` に上げた（dataviz の `validate_palette.js` を `--mode dark` で実行）
- **深緑 `#1c5c45` は濃地に置けない。** 明るいほうの `#79c2a1` を使う

内部ページ（`funnel` / `record` / `roadmap`）は `<style>` にトークンを複製しているので、
site.css と一緒に直す。検査が同期を見ている。

### 配色の切り替えはアニメーションさせない

黒帯に重なると配色が反転するが、**これをフェードさせてはいけない**。
バーの背景が 0.4s かけて変わる間に文字色だけ先に反転すると、
途中でバーも文字も中間色になり、一瞬ヘッダーが読めなくなる（実測 1.91:1）。
スクロールで黒帯を通るたびに起きるので「ヘッダーが消える」と見える。

反転の判定は**ヘッダーの中央**で行う。下端で見ると、まだ半分以上が黒に
重なっているのに配色が戻ってしまう。

黒帯の境目を10px刻みで走査してコントラストを測る検査を e2e に入れてある。

### body の overflow-x

ヒーローのモザイクが画面幅をはみ出す設計なので横方向を切っているが、
`overflow-x: hidden` は body をスクロールコンテナにしてしまい、
**iOS Safari で `position: fixed` のヘッダーが消える既知の組み合わせ**。
対応ブラウザでは `overflow-x: clip`（スクロールコンテナを作らない）を使う。

## 料金の考え方

```
料金 = 基本料金 ¥90,000 ＋ 秒単価 × 合計秒数 ＋ ¥65,000 × (本数 − 1) ＋ ナレーション調整
工数 =        3.0h      ＋ 0.15h × 倍率 × 合計秒数 ＋ 1.5h × (本数 − 1) ＋ 1.0h × ナレーション本数

ナレーション調整（2026-09-22 から本ごとに選べる）
  人物 +¥70,000〜 ／ 1本でも使えば1回ぶん。本数では増えない
  AI   ±0        ／ 料金に含む
  なし −¥25,000  ／ 入れない本1本につき
  松は人の声1名が込み ／ どの本にも人の声を入れないなら手配ぶん −¥25,000
  ※「人物」は画面に出る登場人物のことも指すので、ナレーションの話は「人の声」と書く
```

#### ナレーションは AI と人物の2択（2026-09-17）

| | 料金 | 中身 |
|---|---:|---|
| なし（テロップのみ） | **−¥25,000／本** | AIを込みにしているので、入れない本のぶんは返す |
| AIナレーション | **料金に含む** | 声の選定・速さの調整・配置。**合成音声なので機械の声だと分かる** |
| 人物ナレーション | ¥70,000〜／1名 | 上記＋ナレーターの手配。1人が複数本読んでも手配は1回 |

**使わないなら引く。**AIを料金に含めた以上、テロップだけで済ませる案件から
同じ額を取るのは筋が通らない。**当初 3万で検討したが、
梅15秒×1本だけ ¥21,429/h（目標の93.2%）で下限を割る**ため 2.5万にした
（2.75万でも95.2%しか残らない）。

**松も外せる（2026-09-19）。**以前は人物ナレーション1名に固定していたが、
人物ナレーションが要らない案件で松（登場人物3人・修正3回）を選べなかった。
返す額は「いちばん短い尺でも下限を割らない額」で決めている。松の秒単価に
溶けている人物ぶんは尺に比例するので、短い尺ほど溶けている額が小さく、
**¥70,000 をそのまま返すと 15秒×1本で ¥16,962/h（目標の73.7%）**になる。
**AIに替える −¥25,000／使わない −¥50,000（1本のとき）** なら下限を割らない。
2026-09-22 に本ごとに選べるようにしたので、いまは
**手配ぶん −¥25,000 ＋ 入れない本1本につき −¥25,000** で計算する。
1本だけのときの額は以前と同じ。到達できる全組み合わせ
（合計秒数・本数・なしの本数・人物の有無）で最低 ¥22,381/h。

#### 登場人物の人数は料金に入れない（2026-09-22 決定）

**人数そのものでは変えない。**料金は段で決まる。同じ段の中なら人数で
変わらない（竹の1人と2人は同額）。ただし出せる人数の上限は段ごとに違うので、
**人数が増えて段が上がれば料金も上がる**（0人→1人で梅→竹、2人→3人で竹→松）。

「人数では変わらない」とだけ書くと「何人出しても同じ」に読めるので、
サイトには両方（段の中なら同じ／段が上がれば上がる）を書いてある。

**4人以上は料金表の外。**尺（5分超）と本数（上限超）と同じく
「同じ考え方でお見積りします」に寄せた（2026-09-23）。
それまで人数だけ行き先が書いておらず、
**しかも採用のサンプル（3分）が登場人物4人で、自分のサンプルが上限を超えていた。**
サンプルの注記にも「4人は料金表の上限を超えるので個別見積り」と書いてある。

**ただし取りこぼしが1つある。**キャラクターシート（同じ人物を最後まで
同じ顔で出すための設定）は**実測1.0h/人**なのに、工数モデルは段ごとの
倍率ひとつで、1人でも上限まででも同じ数字になっている。
つまり**2人目・3人目ぶんの工数が価格にも工数にも乗っていない。**

上限まで人を出した場合で全6,478通りを引き直すと、**6通りで下限を割る**。

| 組み合わせ | 料金 | 満員で作った場合 |
|---|---:|---:|
| 松 15秒×1本・なし | ¥139,750 | **¥17,339/h** |
| 松 15秒×1本・AI | ¥164,750 | **¥18,184/h** |
| 竹 15秒×1本・なし | ¥138,500 | **¥20,534/h** |
| 竹 15秒×1本・AI | ¥163,500 | **¥21,110/h** |
| 松 30秒×1本・なし | ¥239,500 | ¥21,538/h |
| 松 30秒×1本・AI | ¥264,500 | ¥21,823/h |

**全部「短い尺・1本」**で、基本料金で吸収しきれない帯。90秒以上や複数本なら問題ない。

**いまは直さない。**見積0件で、15秒に3人出す案件は考えにくい。
値上げに見える変更を、データが無いうちに入れるほうが損。
**実案件で「2人以上出す短い動画」が来たら、そのとき決める。**
直すなら「2人目から1人につき +¥25,000」で下限割れは消える（計算済み）。

**AIは追加料金なし。**合成音声なのでクレジットは約5（¥25）で、
かかるのは原稿・声の選定・配置の 1.0h だけ。ここを有料にすると
「声を入れたいだけ」の相談を落とす。
**人物は本数では増えない**（手配が1回なので）。声を2人使うなら別途見積り。
**工数はどちらも 1本 1.0h。**人物の ¥70,000 の大半はナレーターへの外注費で、
これは工数ではなく原価。だから「¥70,000 ÷ 1.0h」は自分の時間単価ではない。

もともと「1本 ¥30,000」の1択で、合成音声を前提にしていた。
**日本語の合成音声は使えなかった**（4エンジン × 9声を試して全部不採用。
`成果物/サンプル映像/工数記録_サンプル映像03_05_07.md`）。
そこで人物ナレーションを足し、AIは**「機械の声だと分かる」と明記して**料金に含めた。
社内向けや、テロップ主体で声を補助的に使う用途なら成立するため。
**サンプル（01 会社紹介）の音声もAIなので、その旨を注釈に書いている。**

**「〜」は下限。**人物は声によって変わるので、計算機は合計にも「〜」を付ける。
AIは追加料金がないので付けない。

**AIを無料にしたぶん、時間単価の下限が ¥23,750 → ¥22,800 に下がった**
（梅15秒×1本＋AI。目標 ¥23,000 の99.1%）。5%の幅には収まっている。

秒単価は**仕上げの段階**で変わる。松竹梅は**尺ではなく品質**の名前。

**1段上がるごとに増えるものを1つに絞ってある**（梅→竹は「人が出る」、竹→松は「人数が増えて声が込みになる」）。
お客様が迷うのはこの2点だけ。ナレーションを段の壁にしないのは、梅の案件でも
「声を入れたい」は普通に出るから（2026-09-16）。オプションにすれば段を上げずに受けられる。

**差をつけるのをやめたもの**（2026-09-14 の実証による）

| 落としたもの | 理由 |
|--------------|------|
| 画質 4K 対応 | 生成が1080p（Seedance 2.5）で、4K は完成品にアップスケーラをかけただけ。納品先（採用サイト・55インチ）はどちらも1080pで足りる。**サイトから全部消した**（2026-09-16。一度「全段で無料」と特典に戻し、次に FAQ 1問まで減らし、最後に消した。出せない品質は書かない、が結論） |
| 横型・縦型・正方形の3形式 | リフレームはテロップを組み直さないので、縦型が使いものにならない |
| 高精細化・ちらつき除去 | 4K化と同じ処理に含まれ、単独では意味がない。4K と同じ扱い |

**手間が増えないものに価格差をつけると、値付けの根拠ではなく口実になる。**
縦型が必要な場合は機械で切らず、**別の1本として設計する**（2本目 ¥65,000）。

#### 工数の根拠（内部用・画面には出さない）

2026-09-15 の実測（想工業・営業ロープレ、`成果物/〇〇工業_会社紹介動画/工数記録.md`）から
工程別に積み上げ、実案件の打合せ・素材待ち・要件の揺れぶんとして約1.5倍の安全率をかけた。

サンプル映像の実測は別に2本ある。**価格はまだ動かしていない**（受注ゼロで、
価格で落ちたデータが無いため）が、次の見直しで見る材料として置いてある。

| 記録 | 中身 | 効いてくる点 |

| `成果物/サンプル映像/工数記録_サンプル映像03_05_07.md` | 3分＋15秒×2本 | 原価は秒数比例ではない（3分で3.03クレジット/秒、15秒で20.9）。**日本語のナレーションは合成音声では成立しなかった** |

| 段 | 工数倍率 | 実測から積み上げた60秒の工数 | 根拠 |
|----|---------:|---------:|------|
| 梅 | ×1.0 | 7.3h | 構成1.0 ＋ 生成・選別3.0 ＋ つなぎ2.0 ＋ 修正2回1.25 |

ナレーションの工数は段によらず 1本 1.0h。松は1本ぶんが倍率に入っているので、
松が工数として足すのは2本目以降（ここを本数にすると 60秒松の 15.2h が動く）。
料金は AI が込み、人物だけ 1名 ¥70,000〜（上の表）。
工数の 1.0h は自分の作業（原稿・声の選定・配置）だけで、
**ナレーターへの外注費は工数ではなく原価**。

モデル（3.0h ＋ 0.15h × 倍率 × 秒）はこの約1.4〜1.6倍。60秒の松で 15.2h（実測 10.5h）。
以前の 4.8h ＋ 0.24h × 1.0/1.4/1.9 は実測の **3.1倍**で、納期が長く出すぎていた
（5分の松で7週）。価格の倍率 1.0/1.4/1.9 は据え置いたので、時間単価は
梅 ¥26,984 → 竹 ¥29,002 → 松 ¥33,036/h（170通りの平均）と上の段ほど高い。

松の修正を5回から3回に減らしたのは 2026-09-16。実測で1往復 0.625h と分かり、
5回ぶん（3.1h）を秒単価に織り込むと松だけ工数が重く出て、
「竹＋ナレーション」との差が3人目の登場人物だけになるのに価格差が大きく見えるため。
松 ¥6,650 は据え置いた（竹＋ナレ ¥414,000 と松 ¥489,000 の差 ¥75,000 が「3人目」の値段。
ここが通らなければ松を ¥5,900 に下げる）。

**価格は据え置いた（2026-09-16）。** 実測で分かったのは「工数が軽い」ことであって
「市場で通らない」ことではない。受注ゼロで価格で落ちたデータが無いうちは動かさず、
`funnel.html` で落ちる段が見えてからその段だけ下げる。

安全率は e2e で 1.3〜2.0倍に固定してある。実案件で測って外れたら、そちらに合わせる。

#### e2e が守っている不変条件

倍率を動かすときは、次の4つが落ちないことで安全を確かめる。

| 検証 | 内容 |
|------|------|
| 時間単価が目標 ¥23,000 の95%を下回らない | 最低は梅300秒×1本の ¥23,750（目標比103.3%） |
| 時間単価が現実離れしていない | 最高 ¥34,261。計算式が壊れたら跳ねるので検知できる |
| 上の段ほど時間単価が実質的に下がらない | 一時この並びが逆転しており、特典を組み直す理由になった |
| 工数モデルが実測より短くない | 短い側に倒れると納期に遅れる |
| **工数モデルが実測の 1.3〜2.0倍に収まる** | 重すぎると納期が長く出て、時間単価の目標も見かけ上のものになる（以前は3.1倍だった） |
| クレジット原価が梅の秒単価の10%未満 | 41cr/秒 ≒ ¥316/秒（実績は納品74秒ぶんで33cr/秒。安全側の41で見る）。超えるなら秒単価に原価項を足す |
| ナレーションを足しても全体の時間単価が目標を割らない | 人物の ¥70,000 は外注費を含むので「÷1.0h」を単価として使わない。AI・人物それぞれの下限で見る。**下限は「ナレーションなし −¥25,000」の梅15秒×1本（¥22,381）。**納期も +1週以内 |
| 松は人物1名ぶんが ¥0（込み）で、本数では増えない | 計算機の表示・mailto・FAQ の文言が同じ額・同じ単位を指す |
| **「竹＋人物ナレーション」が松より高くなるときは、その場で「松のほうが安い」と出す** | 松は竹＋人物ナレの上位互換なので、黙って逆転させると下位の仕様を高く買う選択肢ができる。短い尺では松の秒単価に溶けているナレーション相当（竹との差 1,750/秒）が ¥70,000 に届かず逆転するため、価格ではなく表示で潰す。AIは無料なので逆転しない |
| mailto が 1,800字に収まる | Outlook の URL 長は約2,048字。松・5分・6本で超えないこと |

以前は「どの組み合わせでも時間単価が一定（±5%）」を検証していたが、
特典を絞って工数の伸びが価格より緩くなり、一定にはならなくなった。
守るべきは一定であることではなく**目標を割らないこと**なので、そちらに変えた。

### なぜ倍率をかけても採算が崩れないか

秒単価の倍率（1.0/1.4/1.9）が工数の倍率（1.0/1.22/1.36）以上なので、
段が上がっても時間単価は下がらない。
全238通り（段×尺×本数×ナレーション3択）をクリックして検証しており、**¥22,381〜34,618/h** に収まる。

### 主観で分けない

「綺麗さ」ではなく、画質・ナレーション・納品形式という**数えられるもの**で分けてある。
主観で分けると「思ったより綺麗じゃない」の水掛け論になり、修正3回無料を食い潰されるため。
ただし数えられればいいわけではなく、**お客様が確かめられるもの**である必要がある。
生成回数は前者は満たすが後者を満たさないので外した。

1回の生成は**4〜15秒**しかつくれない（Cinema Studio 3.0 は4〜15秒、Kling 2.6 は5/10秒）。
長い映像はカットの積み上げなので、工数もクレジットも尺に比例する。
だから秒単価方式が正しい。

### 納期

納期は固定の早見表ではなく**工数から計算**している。
早見表にすると、尺が伸びたときに実際の手間より長い数字を出してしまう（3分48hで5週間など）。

```
納期 = 工数 ÷ 25h（1本に充てられる週あたりの時間） ＋ 1週（確認の往復）   最低2週間
```

`25h` は年間の制作可能時間 1,373h ÷ 46週 ≒ 30h のうち、主軸の1本に充てるぶん。
`1週` は構成案・絵コンテ・初稿チェックの往復。修正を3回とも使う場合は別途1回1週間を見てもらう（本文に明記）。

仕上げの段で工数が変わるので、**納期も段によって変わる**。

| 尺 | 梅 | 竹 | 松 |
|----|---:|---:|---:|
| 15秒〜2分 | 2週 | 2週 | 2週 |
| 3分 | 2週 | 2週 | 3週 |
| 5分 | 3週 | 3週 | 4週 |

本文（制作の流れ・FAQ・構造化データ）の数字が計算結果と一致していることを e2e で見ている。

### 実測できたもの・まだのもの

- **工数は1件ぶん実測済み**（2026-09-15・想工業）。60秒相当の松 10.5h ＋ 15秒版 1.0h、
  修正1往復 0.625h。工程別の内訳は `成果物/〇〇工業_会社紹介動画/工数記録.md`。
  ただし営業ロープレなので、打合せ・素材待ち・要件の揺れは入っていない。
  実案件で測ったら安全率（いま約1.5倍）を実数に差し替えること。
- **1件も受注していない**。価格が市場で通るかのデータがゼロ。とくに5分の松は
  ¥2,085,000 になるが、これが通るかは工数とは無関係の話。`funnel.html` で見る。
- **クレジットは実測 33cr/秒**（納品物 2,462cr ÷ **74秒**）。今回の生成は本編59秒と
  展示会用15秒の**両方ぶん**で、54回生成して24カット採用（本編19・15秒版5）。
  本編の尺だけで割ると 41cr/秒 になるので、**モデルには安全側の 41 を使っている**。
  Max は月5,400なので、60秒級なら月2本。撮り直しが増えた月は足りなくなる。
  実費は ¥310/秒（追加購入単価）で、秒単価の5〜9%。

### 数字を動かすときは

e2e の「どの組み合わせでも時間単価が ¥23,000 の95%を下回らない」を必ず通すこと。

#### ¥23,000/h は目標ではなく、結果の数字（2026-09-21）

決めたのは**価格**と**工数**で、¥23,000 はその割り算。
「この時給が要るから この値段」ではなく「この値段を実測の工数で割ると ¥23,000」。
以前の ¥14,900 も同じで、工数モデルが重かったころの割り算の答え。

**だから「時間単価を下げれば値下げできる」は循環していて、値下げの根拠にならない。**
下げてよいかを決めるのは、必要な年収と働ける時間のほう。

| 時間単価 | 年収1,000万に要る制作時間 | 持ち時間に対して | 月2件のままの年収 |
|---:|---:|---:|---:|
| ¥23,000 | 465h | 34% | ¥9,977,980 |
| ¥17,000 | 629h | 46% | ¥7,193,980 |
| ¥15,000 | 713h | 52% | ¥6,265,980 |
| ¥12,000 | 891h | 65% | ¥4,873,980 |

時間の上では ¥15,000/h でも 1,000万は収まる。**足りないのは時間ではなく件数。**
単価を下げたぶんは件数で埋めるしかなく、件数を増やせるかは営業の話になる。

値下げが効くのは「問い合わせは来るが決まらない」とき。
2026-09-21 時点は「問い合わせが来ない」（見積0件）ので、下げる根拠がまだない。
競合の価格を知ったことは、断られたことではない。
料金表・FAQ（`料金はどうやって決まりますか` と `梅・竹・松は何が違いますか`）・
構造化データ・メール本文の4か所が連動しているので、片方だけ直すと落ちる。

なお **`よくある組み合わせ` は用途名（SNS広告／会社紹介／ブランド映像）**にしてある。
松竹梅が品質の名前になったため、プリセットに使うと二重の意味になるので外した。

後者を消すと、独占性を期待した客先とのトラブルになる。ロゴのように独占性が要る用途は

## 料金計算機の段差（ファネル計測）

料金表を公開しているので、**高いと感じた人は連絡せずに閉じる**。
そのままでは「誰が価格で諦めたか」が一切残らないため、計算機の通過点に印を打っている。
実装は `index.html` の `track()` まわり。氏名・メールなど個人を特定するものは送らない。

| イベント | 意味 |
|----------|------|
| `page_view` | 訪問そのもの（母数） |
| `plans_view` | 料金セクションが画面に入った |
| `calc_use` | **自分で条件を変えた** ＝ 具体的に検討した人。1人1回だけ |
| `calc_preset` | 梅／竹／松のプリセットを押した |
| `calc_result` | 選び終えて金額が出た（連打しても最後の1回だけ） |
| `calc_cta` | 相談ボタン／コピーを押した |
| `calc_leave` | 離脱時の最終状態（`used` / `cta` と、そのときの金額） |

**見たいのは `calc_use` と `calc_cta` の人数の差**。これが価格で落ちた人数。
`calc_leave` に離脱時の `total` が入るので、
「松を見た人だけが落ちている」のか「全体的に落ちている」のかまで分かる。
前者なら松だけ下げればよく、料金表全体を下げる必要はない。

`index.html` の `const ANALYTICS_ID = '';` に GA4 の測定ID（`G-` で始まる）を入れると送信が始まる。
**空のままなら外部には一切送らず、Cookie も置かない**（e2e で固定してある）。

  `about.html` の `#company` にあるコメントを戻す（位置は代表者の下）。
  あわせて JSON-LD に `foundingDate` を足す。
- **郵便番号・番地** — 所在地は**市区町村まで**とする方針。自宅の特定を避けるため、
  表示にも JSON-LD にも入れない。
- **インボイス登録番号** — 未取得。取得したら連絡先の下に行を足す。
- **電話番号** — 個人の携帯なので載せない。営業電話・スパムSMSを避けるため。
  表示にも JSON-LD にも出ていないことを e2e で固定してある。
  載せるなら 050 番号（IP電話）を取ってからにする。

未記入のプレースホルダ（`◯◯`／`（氏名）`／`000-0000` など）を
そのまま公開してしまわないよう、e2e で落ちるようにしてある。

### SNS

YouTube と Instagram（`@so_maru_official`）を、フッター・会社概要・JSON-LD の `sameAs` に載せている。

Instagram の共有URLには `?stkn=...&utm_source=qr` のような**一時トークンが付いてくる**。
これはそのまま配布するものではないので、必ず外して
`https://www.instagram.com/so_maru_official/` の形で貼ること。
トークンが混ざっていないことを e2e で見ている。

投稿を実績欄に自動掲載する仕組みは**入れていない**。
Instagram はログインなしのスクレイピングを弾くので、YouTube と同じ手は使えない。
やるなら Meta Graph API（ビジネスアカウント＋Facebookページ連携＋アプリ審査）が要る。

### 構造化データ

`index.html` の JSON-LD（`Organization`）に、代表者・所在地を入れてある。
**画面の会社概要と同じ値であることを e2e で突き合わせている**ので、
片方だけ直すと落ちる。値を変えるときは両方を直すこと。

まだ確定していない `foundingDate` / `postalCode` / `streetAddress` は入れない。
検索結果に誤った所在地が出るのを避けるため。

### 特定商取引法に基づく表記

いまは置いていない。サイトから直接申し込み・決済を受ける形にする場合は必要になるので、
そのタイミングで別ページとして用意する。

## ロゴ

シンボルマーク（五弁花の線画）＋社名の組み。マークはヘッダー・フッターとも
社名の左に置き、大きさは文字サイズに連動する（`1.62em`）ので画面幅が変わっても比率は崩れない。
社名の区切りは **CSS の図形**で描いたブランド色のハイフン（`.logo-dash`）で、
文字の `-` に戻すとブランドの色が消える。e2e で固定してある。

### 色は深緑（2026-09-24 に金から変えた）

ブランドの色は深緑。ただし**画面に出る値は地の明るさで変わる**。
2026-09-25 に地を濃色にしたので、いま site.css が持っているのは明るいほうの緑。

| | いまの値 | 明るい地だった頃 | 使うところ |
|---|---|---|---|
| `--accent` | `#79c2a1` | `#1c5c45` | 罫線・グラデーション・ロゴの区切り |
| `--accent-ink` | `#8fd0b1` | `#14503c` | 文字（地の上で 9.25:1） |

濃い `#1c5c45` は濃色の地の上では読めないので、**そのまま置いてはいけない**。
白い札（`.stage-mark`）のように下地が白のままの場所だけ、濃いほうを直に書いている。

**金（`#b08733` / `#856420` / `#d9b45f`）は使わない。**
site.css・ロゴの SVG・PNG（lockup / full / ogp）まで入れ替えてある。
`assets/src/` の HTML も同じ値に直した。
検査が「旧ブランド色が残っていないこと」を見ている。

### 2026-09-23 に作り直した

社名が `so-creative` になったのに合わせ、マークを**極彩色の花から五弁花の線画へ**
差し替えた。以前の絵は小さくすると溶け、白黒印刷で成立しなかった
（見積書・請求書・FAX で使えない）。

つまずいた点を3つ残しておく。同じことをやると同じ所で転ぶ。

- **塗りから輪郭を機械的に抜かない。** 花びら1枚ずつの境目が消えて「網のボール」に見えた。
  花びらを1枚ずつ描いて 72 度ずつ回している
- **花びらの先を尖らせない。** 尖るほど葉に近づき、**大麻の葉に見える**
- **枠（viewBox）を目分量で決めない。** 書き出して実測すること。
  小サイズ版は四方が切れていた（絵は x 8.9〜91.1 ／ y 7.2〜86.6 まで広がっていた）

| ファイル | 用途 |
|----------|------|
| `assets/logo-mark.svg` | シンボルマーク（黒）。**サイトが読むのはこれ** |
| `assets/logo-mark-accent.svg` | 同・ブランド色（`#1c5c45`）。大きく出す場所用 |
| `assets/logo-mark-light.svg` | 同・白。暗い地に置く用 |
| `assets/logo-mark-small.svg` | **輪を外して線を太らせた版**（線幅 4.6）。24px 以下はこちら |
| `assets/logo-mark-small-accent.svg` | 同・ブランド色 |
| `assets/logo-mark.png` | マークの PNG（512px）。SVG が使えない場所用 |
| `assets/logo-full.png` | マーク＋社名の縦組み |
| `assets/logo-lockup.png` | マーク＋社名の横組み。明るい地に置く用 |
| `assets/logo-lockup-dark.png` | 同上、暗い地に置く用 |
| `assets/favicon.png` | ブラウザのタブ（64px・透過・輪なし版） |
| `assets/apple-touch-icon.png` | iOS のホーム画面用（180×180・輪なし版） |
| `assets/ogp.png` | SNS 共有時の画像（1200×630） |

### 作り直すとき

`assets/src/` の HTML をブラウザで開いて書き出す（`lockup.html` / `ogp.html` / `full.html`）。
**マークの SVG は元 HTML に直接書いてある。**`<img src>` で読むと、SVG が `viewBox` しか
持たないためブラウザによって幅が 0 になったり、読み込み前に撮ってしまう。
マークを直したら `assets/logo-mark*.svg` と元 HTML の両方を更新すること。

横組みは**旧寸法（749×372）に押し込まない**。社名が長くなって縦横比が変わったので、
押し込むと横に潰れる。参照しているのはこの README だけなので寸法の制約は無い。

### 小さくしたときの見え方

実際にその寸法で描いて確かめてある。**32px から花びらが 5 枚に分かれて読める。**
16px では輪と花びらがくっつくので、輪を外して線を太らせた
`logo-mark-small.svg` に切り替える（ファビコンと iOS アイコンはこちら）。

線画なので単色で成立する。白黒印刷・FAX・印鑑でも同じ形で出るので、
見積書・請求書・契約書にそのまま置ける。

`about.html` はトップのようなスクロール演出やライトボックスを持たず、
ヘッダーの導線もトップへ戻すだけの簡易版にしている(ドロップダウンなし＝ハンバーガーも不要)。
フッターのジャンル一覧はトップの `.genre` カードから生成できないため静的に書いており、
ズレたら e2e で落ちるようにしてある。

## YouTube 新着動画の自動掲載

**2026-09-19 に停止した。**HPから YouTube・Instagram への導線を外す判断に伴い、
Works セクションは自前ホスティングのサンプル8本への静的リンクに置き換え、
ワークフロー（sync-youtube.yml）は削除した。アカウント自体は残っている。

スクリプト（scripts/fetch-youtube.mjs）・設定（youtube.config.json）・
データ（data/videos.json）は残してあるので、復活させるときは
git 履歴からワークフローを戻し、index.html に読み込み側を作り直す。
Secrets の `YOUTUBE_API_KEY` は登録済み（2026-09-19、公式API方式で動作確認済み）。

以下は停止前の記録。

YouTube に動画をアップすると、Works セクションに自動で並ぶ仕組みだった。
APIキー無しでも動く(チャンネルページを読む従来方式)。
Secrets に `YOUTUBE_API_KEY` を登録すると公式の YouTube Data API v3 に切り替わり、
正確な投稿日と説明文が取れて、ページ構造の変更で壊れる心配がなくなる(2026-09-18 実装)。

```
YouTube にアップ
      ↓
GitHub Actions が6時間おきにチャンネルページを取得   (.github/workflows/sync-youtube.yml)
      ↓
data/videos.json を更新してコミット                  (scripts/fetch-youtube.mjs)
      ↓
index.html が読み込んで Works を描画
```

対象チャンネルは `youtube.config.json` で設定します。

```json
{
  "note": "@hzrinrng / ふぞろいの林檎たち",
  "channel": "UCK-RAb4PrWVN4EXXPnbJ67w",
  "maxVideos": 50
}
```

| キー | 説明 |
|------|------|
| `channel` | `UC...`(チャンネルID)/ `@ハンドル` / チャンネルURL のいずれか。ハンドルは変更されうるのでチャンネルID推奨 |
| `maxVideos` | 保存する最大件数(既定 6)。チャンネルページの1画面分=約30件が取得上限なので、50 を指定すれば実質「取れるだけ全部」 |
| `note` | 自由記述のメモ。スクリプトからは無視されます |

### 更新のタイミング

- 6時間おき(`cron: '17 */6 * * *'`)＋ **Actions → Sync YouTube videos → Run workflow** で手動実行
- すぐ反映したいときは手動実行してください

## 取得方式について(重要)

当初は YouTube の RSS フィード(`/feeds/videos.xml`)を使う実装でしたが、
**GitHub Actions のランナーからは UA の有無・リトライに関わらず常に 404 が返る**ことを実測で確認したため、
チャンネルの videos タブに埋め込まれた `ytInitialData` を読む方式に変更しています。

実測結果(GitHub Actions ubuntu-latest、2026-07):

| 対象 | 結果 |
|------|------|
| `youtube.com/feeds/videos.xml`(RSS) | 404(3回リトライ・UA有無いずれも) |
| `youtube.com/channel/{id}/videos` | 200、動画29件を抽出可能 |
| `googleapis.com/youtube/v3/...` | 403(= キーがあれば到達可能) |

### この方式の制約

- **壊れやすい。** YouTube のフロントエンド実装に依存します。実際に旧構造(`videoRenderer`)から
  現構造(`lockupViewModel`)への変更が起きており、今後も変わる可能性があります。
  そのため **1件も抽出できなければスクリプトは異常終了し、`data/videos.json` を書き換えません。**
  ワークフローが赤くなるだけで、サイトは直前の内容を表示し続けます(静かに空データを公開することはありません)。
- **説明文は取得できません。** カードにはタイトルと年のみ表示されます。
- **投稿日は概算です。** チャンネルページは「2 日前」のような相対表記しか持たないため、
  取得時刻から逆算しています(`publishedIsApproximate: true`)。年の表示が境界で1年ずれる可能性があります。

### 公式APIに切り替える(YouTube Data API v3・実装済み)

スクリプトは環境変数 `YOUTUBE_API_KEY` の有無で方式を自動で切り替えます。
キーを登録するだけで公式APIになり、上記の制約(壊れやすい・説明文なし・投稿日が概算)が
すべて解消します。

1. Google Cloud Console でプロジェクトを作り YouTube Data API v3 を有効化、APIキーを発行
2. リポジトリの **Settings → Secrets and variables → Actions** に `YOUTUBE_API_KEY` として登録
3. **Actions → Sync YouTube videos → Run workflow** で手動実行し、ログに
   「YouTube Data API v3 で取得します」と出ることを確認

消費クォータは1回の実行あたり2ユニット(channels.list ＋ playlistItems.list)、
6時間おきで1日8ユニット。無料枠は1日10,000ユニットなので枯渇しません。

方式の差がひとつだけあります。**API はアップロード一覧を読むのでショートも並びます**
(従来方式が読む「動画」タブはショートを含まない)。切り替え初回に23本→41本に増えたのはこれ。
**ショートも並べたままにすると決めた(2026-09-19)。**除外するなら尺で弾く実装が要る。
API 側の投稿日は確定値なので、概算日時の引き継ぎ(mergeWithExisting)は API では使いません。
初回のAPI実行では既存の概算日時が確定値に置き換わる差分が一度だけ出ます。

## 動作の詳細

- **表示件数**: Works は最初の6件を表示し、`More (残数)` ボタンで6件ずつ追加表示します。
  全件出しきるとボタンは消えます。6件以下のときはボタン自体が出ません
- **未設定・データ空・取得失敗のとき**: `index.html` に直接書かれたプレースホルダー(Project 01〜03)が表示されます
- **サムネイル**: `maxresdefault.jpg` を試し、無い動画は `hqdefault.jpg` に自動で切り替わります
- **再生**: カードをクリックするとページ内のライトボックスで再生(`youtube-nocookie.com` 埋め込み)。
  Esc または背景クリックで閉じ、iframe を破棄して再生を止めます。
  JavaScript が無効な環境では YouTube のページに遷移します

node scripts/fetch-youtube.mjs   # data/videos.json を更新
npx http-server -p 8777 .        # http://127.0.0.1:8777 で確認

## 手動で作品を差し替えたい場合

自動掲載を使わず手で管理したいときは、ワークフローを無効化(Actions 画面から Disable)して

## スマホ中心で編集する

このサイトは**スマホだけで編集・公開まで完結**します。PC は常時起動しているので、
Remote Control で繋いでおけば、スマホから出した指示が PC の実ファイルを直接編集します。

```
スマホの Claude アプリ → Code タブ → PC のセッションを開いて指示
      ↓
PC 上で編集される(＝この時点で PC は同期済み。git pull は不要)
      ↓
GitHub の main にプッシュ
      ↓
GitHub Pages が公開                              (数十秒〜数分)
```

### 1. PC 側の設定(最初に1回だけ)

```bash
node scripts/setup-remote-control.mjs
```

`~/.claude/settings.json` に次の3つを書き込みます(既存の設定は保持し、`.bak` を残します)。

| キー | 効果 | |
|------|------|---|
| `inputNeededNotifEnabled` | 許可を求められたとき・質問されたときスマホに通知 | **最重要** |
| `agentPushNotifEnabled` | 長い処理が終わったらスマホに通知 | 重要 |
| `remoteControlAtStartup` | `claude` と打つだけで毎回スマホに繋がる | 接続の土台 |

通知のうち `inputNeededNotifEnabled` がいちばん効きます。Claude Code は許可を求める場面で
**返事があるまで完全に止まる**ため、これが無いと「スマホを見たら1時間前から止まっていた」が起きます。

| オプション | 動作 |
|-----------|------|
| `--dry-run` | 何が変わるか表示するだけ。書き込まない |
| `--check` | 環境の確認だけ。繋がらないときの原因調べに使う |
| `--off` | 3つを `false` に戻す |

### 2. PC 側でセッションを起動しておく

常時起動なので、`tmux` の中で起動します。こうしないとターミナルを閉じた時点で切れます。

```bash
brew install tmux                 # 未インストールなら
cd ~/so-portfolio                 # Mac のフォルダ名は so-portfolio のまま
tmux new -s claude                # claude という名前の常駐枠を作る
claude                            # その中で起動(自動でスマホに繋がる)
```

`Ctrl+b` を押してから `d` で、**起動したまま**ターミナルから離れられます。
戻りたいときは `tmux attach -t claude`。

クラムシェル運用では**スリープした時点で接続が切れます**。これが実運用でいちばん詰まるところです。
確実なのは `caffeinate` で寝かせないことです。tmux ごと包んでしまうのが楽です。

```bash
caffeinate -is tmux new -s claude
```

`-i` はアイドルスリープ、`-s` はシステムスリープを抑止します。この tmux を抜けるまで PC は寝ません。
(システム設定 → バッテリー / ロック画面 側でスリープを切っておく方法でもかまいませんが、
項目名が macOS のバージョンで変わるため `caffeinate` のほうが確実です)

### 3. スマホから繋ぐ

Claude アプリ(iOS / Android)の下部 **Code** タブにセッションが並びます
(PCアイコン＋緑の点＝オンライン)。アプリが未インストールなら Claude Code 内で `/mobile` と打つと QR が出ます。

### 繋がらないとき

```bash
node scripts/setup-remote-control.mjs --check
```

`ANTHROPIC_API_KEY` / `DISABLE_TELEMETRY` / `api.anthropic.com` 以外を指す `ANTHROPIC_BASE_URL` などが
1つでも立っていると Remote Control は起動しません。先にそれを解除してください。
認証は claude.ai アカウント(`claude auth login`)が必要で、APIキー認証では使えません。

PC が落ちている・繋がらないときは、Claude アプリからクラウド上の新しいセッションを始めれば
そちらでも作業できます。ただしそれは PC のファイルを触らないので、
あとで PC 側に `git pull origin main` が必要です。

### 気をつける点

- **公開されるのは `main` の内容だけです。** 作業ブランチのままだとサイトには出ません
- PC で直接編集した場合は、先にコミットしてからスマホで作業を始めてください
